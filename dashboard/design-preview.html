3 行没发出来 · 其中 2 行装的机器不到 5 台，1 行是为了不让人倒推而一起收掉的。 它们一共有多少条事件不报，也不逐行说是卡在哪一条。

条长表示事件数，只在本表内相互比较（最长的那根就是本表最大值）， 不是占比，也不是总量。

为什么这样算

看的是装了它的机器有几台，不是事件有几条 —— 一台机器一天就能产生几十条事件，按事件数算等于把 1 台当成 40 台。不到 5 台就不发布。

「机器太少」和「不知道有几台」是两回事，不能写成一句。 前者是服务端给了台数、确实不够；后者是服务端压根没给台数，我们按不够处理。 把后者说成「太少」，等于替它下了一个我们并没有的结论。

只藏一行是白藏的：总数减掉其他行，就把它算回来了。 所以这时会把最小的那一行也一起收掉 —— 剩下的只是两行的和，拆不开。

为什么没有总计行：有了精确的合计，就有了做减法的起点。 首页这几张表切的是同一批事件，能互相减。

一次安装要多久

how long an install takes

你要看的是同一个动作在新版本上有没有变慢，所以按版本分开比一个总平均有用。 只给 P50 / P95，不给原始耗时 —— 一串按时间排开的毫秒数，本身就是一台机器的轨迹。

2 行没发出来 · 是哪一行卡在哪一条不写出来：逐行的原因本身也是信息。 区间条按本表最大的 p95 相互比较。

为什么这张表比别的表多一道门槛

分位数是从样本里挑出来的一个数：样本一少，p95 正好就等于某一条真实耗时， 发布它等于把那一条原始记录印出来。「至少 5 台机器」管的是人数， 管不住这件事。所以这里另加一道：样本至少 20 条。

20 不是什么证明过的安全线，只是「p95 不再等于最大那一条」的一个保守起点。 要真正稳妥，得让服务端在算的时候就取整或分桶（比如按 50ms 向上取整）。

十一种「没有」，长得都不一样

对一遍这个维度该有哪些取值。

端点通了，回来的是 0 条事件。

真的是 0，不是故障，也不是被筛掉了 —— 我们问到了，答案就是「一条都没有」。 眼下这个 0 说得通：CLI 还没发版，registry 里也还没有制品， 没人装得出一条 install 事件来。

等第一个用户装成功一次，第一条事件就来了（自动上报每台机器每天最多一条）。

它和下面的「维度是空的」，是这里仅有的两个不换底色、不带色条的格子—— 它们都是结论，不是异常。给结论加色条，就是把结论说成了故障。

服务端算了这个维度，但一行都没有。

有事件，服务端也算了这个维度 —— 它就是空的。最常见的原因是这批事件本来就不带这个字段： artifact / version / client / scope / ms / reason 都是选填， 比如 rollback / sync-lock 这类事件本来就没有 artifact。这不是故障，也不是「没人用」。

想知道那批事件去哪了，看「按动作」那张表 —— 那个字段是必填的，一条都不会漏。

未发布

有数，但一行分位数都发不出来。

这张表比别的表多一道门槛：除了机器台数，还要求事件条数够。 所以别读成「机器不够」：也可能机器够多，只是每台才装过一两次。

版面从上往下的顺序，就是判断的顺序（有没有数据源 → 回来的东西对不对 → 有没有事件 → 维度 → 筛选 → 能不能发布）：数据源那一级的提示在最上面， 维度那一级在各自面板里，行那一级在表格里。 倒过来放，人会先看到「这张表发不出来」，往上滚才发现端点根本没连上。

口径与边界

scope and boundaries

说得长一点的都放在这里。但它替代不了顶上那一条 —— 一个只看首页、从没点进来过的人，也必须知道那三件事。

为什么这个平台永远不提供「按 install_id 下钻」

install_id 是本机生成的随机 UUID，跟账号、机器名、用户名都对不上， 单看它确实指不到人。但只要有一个界面能把某个 install_id 的事件 按时间排开，它本身就成了一件认人的工具：排出来的是 「这台机器哪天装了什么、什么时候卸的、用的哪个系统和哪版 CLI」的完整轨迹。 源 IP 加上一个稳定的 install_id 再加上时间线，就等于盯住了一台机器。 IP 那一半，端点侧已经用「不记 IP、不记 UA」掐掉了； 时间线这一半，在我们手里。

所以拦它的办法是结构上的，不靠自觉：字段按白名单正向取、 归一化的时候把任何像标识符的键都剥掉、样本太少就不发布。想加下钻，得先去改规格。

已知的残余风险：跨表相减

首页这几张表切的是同一批事件。再配上一点外部知识， 理论上可以拿几张表互相相减，把某一张里没发布的行推出来。

我们做到的：每张表都不给总计行；没发布的那一组不报合计； 只要有哪张表没发全，顶上那个总数就只给区间 —— 减出来的也只是一个区间。

我们做不到的：一个绝对的保证。行数、枚举里缺了哪个取值、 两张表行数的差，都还是线索。要真正堵死，得把这一整套表放在一起算能不能被解出来， 那只能在服务端做。

这一条写在页面上而不是藏起来 —— 看这个后台的人有权知道它的保证到哪为止。

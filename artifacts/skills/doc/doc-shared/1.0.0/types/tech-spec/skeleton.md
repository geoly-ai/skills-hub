# 技术 Spec 骨架

对齐 design.md §5.4；写作约束采用 lark-doc genres/technical-doc.md 的 design_rfc 模式：证据 → 取舍 / 设计 → 验收。

「文档控制与修订记录」「摘要」不再是骨架里的编号章节：前者由引擎按 doc.json（status、reviewers、related_docs、version、revision_history）自动生成封面文档控制表与修订记录页；后者由正文的 `<!-- summary --> … <!-- /summary -->` 块生成摘要页。写作者在这两处写内容，不要在正文再起一章重复（2026-09-15 第三波去重，见 pack-interface.md）。summary 块必须回答：要解决什么、推荐方案、主要代价。

## 各节写法要点与反例

### 文档控制与修订记录（引擎生成，不在正文写）
- 状态、评审人、关联 PRD、版本、修订记录改为写进 doc.json（status、reviewers、related_docs、version、revision_history），由引擎生成封面文档控制表与修订记录页；正文不再重复一章。要点仍然适用：① 状态三态（草稿 / 评审 / 批准）。② 评审人应包含至少一位非本方案作者的资深工程师。③ 关联 PRD 引用具体 REQ 编号而非笼统"相关需求"。
- 反例：评审人只有方案作者本人——不构成有效评审。

### 摘要（`<!-- summary -->` 块，不是编号章节）
- 要点：① 「要解决什么」用问题陈述，不用方案名称代替。② 推荐方案一句话说清核心机制。③ 主要代价要诚实，包括迁移成本、性能取舍、维护负担，不能只讲收益——它会被引擎单独渲染成一页。
- 反例：「本文介绍积分系统的技术方案」——没有说清问题、推荐方案、代价。

### 背景与问题
- 要点：① 现状用具体证据描述（代码位置、现有架构缺陷的量化表现），不用主观感受。② 为什么现在做要给出触发因素（业务目标、故障、规划节点）。③ 与关联 PRD 的问题描述要一致，不能另起炉灶。
- 反例：「现有系统比较老旧」——老旧不是证据，缺具体的架构缺陷描述。

### 目标、非目标与约束
- 要点：① 不变量要写清"改动后必须仍然成立的事实"（如"积分流水不可篡改"）。② 性能与兼容约束要给数字门槛。③ 非目标要与备选方案节呼应，说明为什么某些方向不在本次改动范围。
- 反例：「保证系统稳定」——不是可验证的不变量。

### 现状架构
- 要点：① 现状架构图要真实反映当前系统结构，不是理想化描述。② 图后必须有文字等价说明（design_rfc 规则：图不能是唯一证据）。
- 反例：只贴图不写文字说明——图不能替代文字，读者无法在不看图的情况下理解现状。

### 方案设计
- 要点：① 架构图、时序图、ER 图、状态机按需求覆盖，每张图有图号、被引用、图后有文字等价说明。② 组件职责要写清每个组件"负责什么、不负责什么"的边界。③ 关键流程要覆盖正常路径与至少一个异常分支。
- 反例：架构图画得很漂亮，但正文没有一句话解释每个组件的职责——图成了唯一证据，违反 design_rfc 规则。

### 接口设计
- 要点：① 接口签名、输入约束、错误码、幂等性、版本策略都要覆盖，缺哪项写明不适用理由。② 与 api-reference 类型包的边界：本节只覆盖本方案新增或变更的核心接口，完整的 API 文档属于 api-reference。
- 反例：接口表只有请求路径，没有错误码列——调用方无法处理失败场景。

### 备选方案与取舍
- 要点：① 至少两个真实可行方案，不能是"方案 A（推荐）+ 方案 B（故意做弱的稻草人）"。② 同口径比较：用同一组维度（成本、性能、迁移难度、风险）比较所有方案。③ 否决理由要具体，不能只写"更复杂"。
- 反例：备选方案 B 描述只有一句话且明显不可行——不是真实备选，是为了凑数。

### 失败、安全与兼容
- 要点：① 失败模式要覆盖关键依赖失败（如下游服务超时、数据库不可用）时系统的行为。② 降级策略要具体，不能只说"优雅降级"。③ 权限、数据安全按实际风险纳入，不机械套模板。④ 向后兼容要说明旧数据 / 旧客户端如何处理。
- 反例：「系统会自动处理异常情况」——没有说明具体的失败模式与降级动作。

### 迁移、上线与回滚
- 要点：① 步骤要可执行，写清顺序与依赖。② 开关（功能开关 / 灰度开关）要具体到配置项。③ 回滚判据要可核验（如"错误率超过 X% 触发回滚"），并写清回滚是否可能丢数据。
- 反例：「如果出问题就回滚」——没有判据、没有具体步骤，无法执行。

### 可观测性
- 要点：① 指标要覆盖方案设计里的关键路径（如接口延迟、失败率）。② 日志要说明关键事件会记什么字段。③ 告警要给阈值与触达对象。
- 反例：「会打日志监控」——没有具体指标、阈值、告警对象。

### 测试与验收
- 要点：① 测试策略要说明覆盖单元、集成、压测等哪些层次。② 验收判据要可核验，并链接到测试计划文档。③ 与关联 PRD 的验收标准呼应，不能自说自话。
- 反例：「测试通过即可上线」——没有说明测什么、判据是什么。

### 未决问题
- 要点：① 每条未决问题要有 owner 与截止时间。② 未决问题不应包含"会不会做"这类应在评审阶段解决的问题，只放技术细节未决项。
- 反例：「要不要做这个方案，待定」——这是评审阶段该关闭的问题，不应作为未决问题遗留到批准状态的文档里。

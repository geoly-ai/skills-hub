# 会员积分系统 v2 技术方案设计（Tech Spec）

<!-- summary -->
v1 的积分规则（获取比例、抵扣比例、上限、有效期）硬编码在积分服务的业务代码里，每次运营调整规则都要走一次完整的产品排期与代码发布流程，平均周期 9 个工作日（见 PRD 背景）。同时，兑换链路在压测中发现并发扣减库存存在竞态条件，理论上可能超卖（PRD REQ-REDEEM-04 明确要求原子性）。推荐方案：新增独立的「规则引擎服务」，把规则参数从代码中抽出，运营通过后台配置并即时生效；账户服务与兑换服务改为在关键路径上同步查询规则引擎（带本地缓存）。兑换扣减改用数据库行锁（SELECT ... FOR UPDATE）+ 幂等键的方案，替代 v1 的「先查后扣」非原子实现。主要代价：新增一个独立服务带来额外的部署与监控成本；迁移期新老规则引擎需要双写并交叉校验约 2 周，期间规则变更仍需双边操作，运营响应速度提升的收益要到迁移完成后才体现。
<!-- /summary -->

## 1. 背景与问题

v1 积分服务（points-service，单体，Java）的规则参数写死在 PointsRuleConstants.java 中，2026 年 Q2 运营提出 11 次规则变更需求，平均从提出到上线 9 个工作日（数据来源：Jira 工单周期统计，见 PRD 背景）。

压测证据：2026-07 对兑换接口做并发压测（100 并发，目标商品剩余库存 5 件），复现出 3 次超卖（实际扣减 8 件），根因是「查询库存 → 判断充足 → 扣减库存」三步非原子，存在竞态窗口（压测报告见内部 Confluence，链接从略）。

现在做的触发因素：PRD v1.2 已批准，REQ-RULE-01/02（运营可配置规则）与 REQ-REDEEM-04（并发原子扣减）是本期 P0 需求，必须在技术上给出可落地方案才能进入开发排期。

## 2. 目标、非目标与约束

### 2.1 不变量

- 积分流水一旦写入不可篡改，只能通过新增反向流水（扣减/回收记录）冲正，不允许物理删除或修改历史流水。
- 兑换扣减库存与扣减积分必须在同一事务边界内完成，不允许出现「扣了积分但兑换失败」或反之的中间状态。

### 2.2 性能与兼容约束

<!-- table: 约束门槛 -->
| 类别 | 门槛 |
|---|---|
| 规则查询接口延迟 | 95 分位 < 50ms（含本地缓存命中） |
| 兑换接口延迟 | 95 分位 < 300ms（对齐 PRD 非功能需求） |
| 兼容性 | v1 遗留积分流水数据结构不变，新规则引擎需兼容读取 |

## 3. 现状架构

![现状架构](figures/current-arch.fig.json){#fig:current-arch}

如 @fig:current-arch 所示，v1 的积分服务是单体应用，规则参数以常量形式编译进服务代码，账户读写与兑换逻辑共享同一个数据库实例，没有独立的规则配置入口，运营变更规则必须经过「提需求 → 改代码 → 测试 → 发布」完整链路。

## 4. 方案设计

### 4.1 架构

![目标架构](figures/target-arch.fig.json){#fig:target-arch}

如 @fig:target-arch 所示，新增「规则引擎服务」（rule-engine-service）独立部署，负责规则的存储、生效时间调度与灰度分流，对外提供规则查询接口；账户服务（account-service）与兑换服务（redeem-service）在获取 / 消耗的关键路径上同步调用规则引擎（带本地缓存兜底，见 §7），不再各自维护规则副本。运营后台（admin-console）直接对接规则引擎服务做配置与人工调整审计。组件职责边界：规则引擎服务只负责「规则是什么、何时生效」，不参与积分计算；账户服务负责积分余额与流水的原子性；兑换服务负责库存协同与兑换单生成。

### 4.2 关键流程时序

![积分兑换流程时序图](figures/sequence.mmd){#fig:sequence}

如 @fig:sequence 所示，兑换请求先由兑换服务查询规则引擎确认叠加限制（REQ-REDEEM-03），再在同一数据库事务内对积分账户与商品库存加行锁校验并扣减；正常路径下事务提交后生成兑换单，异常分支（余额不足 / 库存不足 / 规则冲突）在加锁校验阶段即返回明确错误码，不进入扣减步骤，避免部分扣减的中间状态。

### 4.3 数据模型

![积分核心数据模型](figures/data-model.mmd){#fig:data-model}

如 @fig:data-model 所示，积分账户（POINTS_ACCOUNT）与流水（POINTS_LEDGER）一对多，每笔流水关联一条规则快照（RULE_SNAPSHOT，记录生效时使用的规则版本，用于审计与回溯，而不是实时引用规则引擎当前配置，避免历史流水因规则后续变更而「改写」含义）。

### 4.4 状态机

![兑换单状态机](figures/state-machine.mmd){#fig:state-machine}

兑换单的状态机覆盖「待处理 → 处理中 → 已完成 / 失败 → 失败可重试回到待处理」的完整路径，与 §4.2 时序图的异常分支对应。

## 6. 备选方案与取舍

### ALT-1：独立规则引擎服务 + 行锁原子扣减（推荐）

规则参数从代码中完全抽出为独立服务，账户 / 兑换服务同步查询（带缓存）；兑换扣减用数据库行锁保证原子性。

### ALT-2：规则参数配置化但不拆服务，扣减改用分布式锁

规则参数改存数据库配置表，但仍由积分服务本身读取，不新增独立服务；兑换扣减用 Redis 分布式锁代替数据库行锁。

<!-- table: 方案比较 -->
| 维度 | ALT-1（推荐） | ALT-2 |
|---|---|---|
| 成本 | 新增一个服务的部署与监控成本 | 无新增服务，但需要引入并运维 Redis 分布式锁组件（团队现无该组件的生产经验） |
| 性能 | 规则查询本地缓存命中下延迟极低；行锁在高并发同商品场景下有排队等待 | 分布式锁同样有排队等待，且存在锁续期失败导致误判的已知风险类别 |
| 迁移难度 | 需要新老规则双写校验约 2 周 | 改动面更小，预计 1 周 |
| 风险 | 规则引擎服务本身的可用性成为新的单点，需要缓存兜底 | 分布式锁的正确性依赖团队缺乏经验的组件，已知故障模式（锁续期失败、脑裂）应对成本更高 |

否决 ALT-2 的理由：团队此前没有生产环境运维 Redis 分布式锁的经验，而数据库行锁是团队熟悉且已有故障处理经验的方案；ALT-2 表面上迁移更快，但引入了团队难以快速定位的新故障类别，与「降低兑换失败率」的核心目标相悖。

## 7. 失败、安全与兼容

<!-- table: 失败模式与降级 -->
| 失败模式 | 触发条件 | 降级动作 |
|---|---|---|
| 规则引擎服务不可用 | 服务健康检查连续失败 | 账户 / 兑换服务读取本地缓存的最近一次有效规则（缓存 TTL 10 分钟），超过 TTL 仍不可用则拒绝新的获取 / 兑换请求并返回明确错误，不使用过期规则做静默降级 |
| 数据库行锁等待超时 | 同商品高并发兑换 | 超时请求返回「请稍后重试」错误码，不做无限重试，避免雪崩 |

权限：规则配置接口与人工调整接口要求运营角色 + 二级审批（超权限金额，见 PRD REQ-ADMIN-01）。数据安全：规则快照与流水记录留存审计日志，不对外暴露其他会员数据。向后兼容：v1 遗留流水数据结构不变，迁移脚本只新增规则快照关联字段，不改写历史记录。

## 8. 迁移、上线与回滚

### 8.1 迁移步骤

1. 部署规则引擎服务，导入 v1 现有规则参数作为初始配置。
2. 账户 / 兑换服务接入规则引擎查询接口，但暂不下线 v1 内置规则逻辑，双写并交叉校验结果一致性，为期 2 周。
3. 校验通过后，账户 / 兑换服务切换为只信任规则引擎结果，下线内置规则逻辑。
4. 灰度 5% 会员验证兑换扣减新链路（行锁方案），观察行锁等待与超时率。
5. 全量切换。

### 8.2 回滚判据

> [!decision]
> 回滚条件：灰度期兑换失败率高于迁移前基线，或规则引擎服务可用性低于 99.9%，连续观察窗口 1 小时触发回滚。回滚是否可能丢数据：不会，回滚只切换服务调用路径回 v1 内置规则逻辑，双写期产生的流水数据结构未变更，不需要数据迁移回滚。

## 10. 测试与验收

测试策略覆盖单元测试（规则引擎的生效时间与灰度分流逻辑）、集成测试（账户 / 兑换服务与规则引擎的接口联调）、并发压测（复现并验证 §1 提到的超卖场景已修复）。验收判据：并发压测（100 并发、目标商品库存 5 件）连续 3 轮无超卖；灰度期兑换失败率连续 7 天 < 2%。详细测试用例见《会员积分系统 v2 测试计划》与《测试用例》。

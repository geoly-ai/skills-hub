# API 参考骨架

对齐用户指令「api-reference 按 lark-doc technical-doc 的 api_reference 模式：接口总览、鉴权、通用约定（分页、幂等、错误码表、版本）、每个接口的请求/响应表与示例代码块（标语言）、变更记录」，写作规则见 writing-contract.md。

「文档控制与修订记录」不再是骨架里的编号章节：由引擎按 doc.json（status、owner、reviewers、related_docs、version、revision_history）自动生成封面文档控制表与修订记录页，正文不要再起一章重复（2026-09-15 第三波去重，见 pack-interface.md）。

| id | 标题 | 必备 | must_answer |
|---|---|---|---|
| overview | 接口总览 | 是 | 服务边界、base URL、接口清单一览表 |
| auth | 鉴权 | 是 | 鉴权方式、凭证获取、权限范围 |
| conventions | 通用约定 | 是 | 分页、幂等、错误码表、版本策略 |
| endpoints | 接口详情 | 是 | 每个接口：签名、权限、输入约束、行为/副作用、输出、错误、示例 |
| rate-limits | 限流与重试 | 按需 | 限流规则、重试建议、退避策略 |
| compat | 兼容与弃用 | 按需 | 弃用接口清单、迁移指引、下线时间 |
| changelog | 变更记录 | 是 | 版本、日期、变更内容、是否破坏性 |

## 各节写法要点与反例

### 文档控制与修订记录（引擎生成，不在正文写）
- 状态、owner、评审人、关联 tech-spec、版本、修订记录改为写进 doc.json，由引擎生成封面文档控制表与修订记录页。要点仍然适用：① 关联 tech-spec 用 related_docs 回填。② owner 应为该服务的技术负责人，能对外部调用方的问题负责。
- 反例：owner 写团队名而非具体人，调用方遇到问题找不到人。

### 接口总览
- 要点：① base URL 要写清环境区分（测试 / 生产）。② 接口清单一览表至少含方法、路径、简述、状态（稳定 / Beta / 已弃用）四列，方便调用方快速定位。③ 服务边界要说明"这个服务负责什么，不负责什么"，避免调用方误用。
- 反例：只给一个接口列表没有简述和状态列——调用方无法判断该用哪个接口、能不能放心用。

### 鉴权
- 要点：① 鉴权方式要具体（如 Bearer Token、HMAC 签名），不能只写"需要鉴权"。② 凭证获取流程要可执行。③ 权限范围（scope）要与接口详情节的"权限"列对应。
- 反例：「调用需要登录态」——登录态怎么获取、放在请求的哪个位置，都没写。

### 通用约定
- 要点：① 分页参数与响应结构统一说明一次，接口详情节不重复贴分页字段解释。② 幂等策略要写清哪些接口支持幂等、幂等键怎么传。③ 错误码表要覆盖全局通用错误码（如鉴权失败、限流），接口专属错误码放在各接口详情里。④ 版本策略要说明版本号出现在哪（URL / Header）以及升级策略。
- 反例：错误码表只写了 200 和 500——没有覆盖业务错误码，调用方无法据此做异常处理分支。

### 接口详情
- 要点：① 每个接口写清签名（方法 + 路径）、权限要求、输入约束（必填/可选/类型/取值范围）、行为与副作用（会不会产生幂等外的连带效果）、输出结构、已知错误及可操作的恢复建议。② 请求与响应都要有示例代码块并标语言。③ 副作用（如触发通知、扣减库存）要显式写出，不能让调用方通过试错发现。
- 反例：只给了一个成功响应示例，没有列出该接口可能返回的错误码与含义——调用方遇到失败无法判断怎么处理。

### 限流与重试
- 要点：① 限流规则要给具体数字（如"100 次/分钟/IP"）。② 重试建议要说明哪些错误码可重试、退避策略（如指数退避）。
- 反例：「请勿频繁调用」——没有具体限流数字，调用方无法自查是否超限。

### 兼容与弃用
- 要点：① 弃用接口要写清替代方案与下线时间。② 迁移指引要具体到字段级差异。
- 反例：「该接口即将废弃」——没写替代方案和下线时间，调用方无法规划迁移。

### 变更记录
- 要点：① 每条变更标注是否破坏性（breaking change）。② 破坏性变更要说明影响范围与迁移建议。
- 反例：变更记录只写"优化了接口"——没有说明具体改了什么、是否破坏性。

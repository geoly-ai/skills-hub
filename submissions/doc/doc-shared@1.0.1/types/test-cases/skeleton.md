## 写法要点与反例

### 用例编号与标题
- 要点：① 编号唯一，模块前缀与关联需求模块一致。② 标题动词开头（"查询…""兑换…""校验…"），一句话说清测什么。
- 反例：标题写「积分」——不是动作，看不出测的是什么行为。

### 关联需求
- 要点：① REQ 编号必须能在关联 PRD 中找到（跨文档校验，见 qa-rules.md CASE-02）。② 一条用例可以关联多个需求（如同时验证获取与通知两条需求的联动），但主用例应尽量对应单一需求，联动场景单独标注。
- 反例：关联需求写「无」或留空——无法纳入覆盖矩阵统计。

### 前置条件与测试步骤
- 要点：① 前置条件要具体到可复现的状态（账户余额、订单状态等），不写"正常情况下"。② 测试步骤要编号且可复现，不能跳步（如"检查结果是否正确"这种缺少具体操作的步骤）。
- 反例：步骤写「1. 测试功能是否正常」——不是可执行的步骤。

### 测试数据
- 要点：① 给具体数值或标识符（订单号、会员号、金额），不写"任意数据"。② 不含真实隐私数据，用虚构 ID。
- 反例：测试数据留空且步骤里也没有具体数值——无法复现同样的测试条件。

### 预期结果
- 要点：① 预期结果要与步骤逐条对应或明确标注为整体结果。② 不用"正常""成功"单独出现而不加限定（如"到账成功"可以，单独一个"正常"不行，见 CASE-04）。③ 预期结果要能与关联需求的验收标准对上。
- 反例：预期结果写「结果正常」——正常是什么状态，无法核对。

### 类型与优先级
- 要点：① 类型要覆盖异常、边界、并发这类高风险点，不能全是"功能"类型。② 优先级要与关联需求的优先级大体匹配（P0 需求的核心用例通常也是 P0），但允许有差异（如 P0 需求的边界用例可以是 P2）。③ 异常类用例占比不宜过低（阈值由包配置，本样张约 35%）。
- 反例：47 条用例全部标"功能"类型——没有覆盖异常、边界、并发场景，测试深度不足。

# PRD 骨架

对齐 design.md §5.2；与 lark-doc genres/prd.md 的内容逻辑一致：用户问题 / 证据 → 目标 / 结果 → 范围 / 非目标 → 场景 → 行为需求 / 验收 → 异常 / 边界 → 适用质量约束 → 依赖 / 开放问题。

「文档控制与修订记录」「摘要」不再是骨架里的编号章节：前者由引擎按 doc.json（status、owner、reviewers、related_docs、version、revision_history）自动生成封面文档控制表与修订记录页；后者由正文的 `<!-- summary --> … <!-- /summary -->` 块生成摘要页。写作者在这两处写内容，不要在正文再起一章重复（2026-09-15 第三波去重，见 pack-interface.md）。summary 块必须回答：一句话问题、目标、范围、上线判据。

## 各节写法要点与反例

### 文档控制与修订记录（引擎生成，不在正文写）
- 状态、owner、评审人、关联 MRD / Spec、版本、修订记录改为写进 doc.json（status、owner、reviewers、related_docs、version、revision_history），由引擎生成封面文档控制表与修订记录页；正文不再重复一章。要点仍然适用：① 状态取「草稿 / 评审中 / 已批准」三态之一。② owner 与评审人写真实姓名或角色。③ 修订记录只记「做了什么改动」。

### 摘要（`<!-- summary -->` 块，不是编号章节）
- 要点：① 一句话问题用「谁 + 遇到什么 + 后果」句式，不写解决方案。② 目标与范围各一句，禁止贴功能列表当摘要。③ 上线判据写可核验的条件（如「P0 需求验收通过 + 覆盖率 ≥ 90%」），不写「效果好」。④ 摘要独立可读，不依赖后文才能理解——它会被引擎单独渲染成一页，读者可能只看这一页。
- 反例：「本 PRD 定义了会员积分系统的功能需求」——没有回答问题、目标、范围、判据中任何一项，等于没写摘要。

### 背景与用户问题
- 要点：① 先写谁（角色/细分），再写情境，再写问题，顺序不能倒。② 每个问题陈述后面跟证据来源（数据、工单号、访谈引用），无来源的判断标注「待补证据」。③ 不用「用户反馈很多」这类无法核实的说法，给具体数量或抽样方式。④ 区分「用户说的」和「我们推断的」。
- 反例：「用户普遍认为积分不好用」——普遍是几成？哪个细分？证据是什么？三问三不答。

### 目标与指标
- 要点：① 每个目标配一个可观测指标，指标写清口径（分子分母）、数据来源系统、统计时间窗。② 目标值未知时用「[目标值待产品/数据确认，owner：xxx，截止：日期]」占位，不编数字。③ 目标与范围必须能互相推导，目标里出现的能力范围里必须覆盖。④ 避免只写方向不写量级的目标（如「提升活跃」）。
- 反例：「提升用户活跃度」——没有指标口径、没有来源、没有目标值，无法验收。

### 范围与非目标
- 要点：① 非目标节必须非空，且要写清「为什么不做」而不是只列条目。② 范围与非目标不能自相矛盾（同一能力不能既在范围又在非目标）。③ 范围用能力清单而非页面清单，避免把实现细节写进范围。④ 阶段性范围（本期 / 下期）分开写，不要混在一张表里不分期。
- 反例：范围写「支持积分兑换」，非目标又写「不支持积分兑换实物」——如果这属于本期该做的子能力，属于矛盾表述，需要拆清楚。

### 用户与场景
- 要点：① 角色用业务语言命名（如「新会员」「高等级会员」），不用系统内部代号。② 每个关键场景写正常路径，至少一个场景配流程图并用 {#fig:x} 标注、正文用 @fig:x 引用。③ 场景要覆盖后文功能需求里引用到的所有前置情境，不能有需求找不到对应场景。④ 场景不等于用例，不写测试步骤级别的细节。
- 反例：场景只写「用户登录 App」——登录不是本文档的场景，缺少与积分相关的具体任务情境。

### 功能需求
- 要点：① 每条需求编号唯一、连续，模块缩写与 numbering 规则一致。② 需求描述可观察行为（"系统在 X 时展示 Y"），不暗藏实现方案（"用 Redis 计数器实现"这类技术选型不出现在 PRD）。③ 异常与边界必须覆盖至少一种失败路径，不能只写正常路径。④ 验收标准要能直接转成测试用例的预期结果，用可核验的语言，不用「合理」「友好」这类形容词。⑤ 优先级要有区分度，不能全部 P0。
- 反例：「REQ-EARN-01：系统支持积分获取，使用消息队列异步处理」——把实现方案（消息队列）写进了需求，且没有触发条件、异常路径与验收标准。

### 非功能需求
- 要点：① 每项配可核验门槛（如「95 分位延迟 < 500ms」），无法量化的写清判定方式。② 不适用的类别要写不适用的理由，不能直接省略整类。③ 安全 / 隐私类只按实际风险纳入，不机械套模板。④ 与功能需求的关联要写清是全局约束还是特定需求的约束。
- 反例：「性能：系统要快」——快到什么程度、怎么测，都没有，等于没写。

### 数据与埋点
- 要点：① 每个事件写清触发时机、属性字段与口径，不只列事件名。② 埋点与目标指标（goals 节）能对上，指标要用到的事件都在这里定义。③ 敏感字段标注是否涉及个人信息、是否需要脱敏。
- 反例：埋点表只有「事件名」一列——缺属性、缺触发时机，无法用于统计目标指标。

### 依赖、风险与开放问题
- 要点：① 每条依赖写清依赖方与交付时间。② 每条开放问题必须有 owner 与截止时间，没有 owner 的问题不能进最终版。③ 风险要写应对或监控方式，不只罗列风险本身。
- 反例：「开放问题：积分有效期怎么定，待讨论」——没有 owner、没有截止时间，永远停留在待讨论。

### 里程碑
- 要点：① 阶段划分与判据挂钩，不写日历日期式的硬承诺（除非确已排期）。② 每个阶段的判据要可核验。
- 反例：「二期：优化体验」——不是可核验的判据。

### 附录：术语表
- 要点：① 只收录本文档内反复出现、容易产生歧义的术语。② 术语定义与 glossary.json 声明的禁用同义写法保持一致。

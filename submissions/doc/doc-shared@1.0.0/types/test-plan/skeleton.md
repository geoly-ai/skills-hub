## 各节写法要点与反例

### 文档控制（引擎生成，不在正文写）
- 状态、owner、评审人、关联 PRD / Spec、版本、修订记录改为写进 doc.json，由引擎生成封面文档控制表与修订记录页；被测版本写进 summary 块的第一句。要点仍然适用：① 被测版本要具体到可核实的版本号或代码提交，不写"最新版"。② 关联 PRD / Spec 用 related_docs 回填，不只写名称。
- 反例：「被测版本：最新版本」——发布多次后无法确定具体测的是哪个版本。

### 测试范围与不测范围
- 要点：① 范围要覆盖 PRD 的功能需求模块，逐一对应。② 不测范围必须给理由（如"依赖尚未就绪""风险评估后判定优先级低"），不能只列条目。③ 平台/版本组合要具体（如"iOS 17+、Android 12+"）。
- 反例：「不测范围：等级模块」——没有给理由，评审人无法判断是否合理。

### 测试策略
- 要点：① 每种测试类型要说明用什么方法（手工/自动化/工具）。② 自动化比例要给数字并说明覆盖范围。③ 策略要与被测需求的风险等级匹配（高风险需求配重的测试方法）。
- 反例：「全面测试」——没有说明具体类型、方法、比例。

### 环境与数据
- 要点：① 环境清单要具体到域名/配置差异。② 测试账号要说明权限与数量。③ 测试数据准备方式要具体，避免用生产真实数据（涉及隐私风险）。
- 反例：「用测试环境测试」——没有说明哪个测试环境、数据从哪来。

### 准入与准出标准
- 要点：① 准入标准要可核验（如"冒烟测试通过率 100%"）。② 准出标准要给缺陷级别与数量门槛、用例通过率门槛。③ 与测试报告的准出结论直接对应，不能事后改口径。
- 反例：「测完就能上线」——没有量化标准。

### 进度与人员
- 要点：① 阶段划分要与测试策略的类型对应。② 每个阶段要有负责人，不是集体名词。
- 反例：进度表只有开始结束日期，没有负责人。

### 风险与应对
- 要点：① 风险要具体到"什么条件下会发生什么后果"。② 应对措施要可执行。
- 反例：「测试时间可能不够，尽量加快」——不是可执行的应对措施。

### 缺陷管理
- 要点：① 级别定义要给判定标准（如"P0：核心链路不可用"）。② 流转要写清状态与责任人切换规则。
- 反例：「缺陷分为严重和一般」——没有判定标准，不同人会有不同理解。

### 需求覆盖矩阵
- 要点：① 矩阵按 REQ × TC 生成，每条 P0/P1 需求至少关联一条用例（D2 门判据）。② 矩阵要能自动从 data/requirements.csv 与 test-cases 的 data/cases.csv 交叉生成，不是手工维护的静态表。③ 覆盖为 0 的需求要显式标红或标注原因。
- 反例：矩阵只列了功能需求的一部分，且没有标注哪些需求尚未覆盖——无法判断测试计划是否完整覆盖了 PRD。

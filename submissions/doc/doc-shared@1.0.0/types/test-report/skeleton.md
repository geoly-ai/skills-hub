「文档控制」不再是骨架里的编号章节：由引擎按 doc.json（status、owner、reviewers、related_docs、version、revision_history）自动生成封面文档控制表与修订记录页，正文不要再起一章重复（2026-09-15 第三波去重，见 pack-interface.md）；被测版本写进 summary 块，报告日期用 revision_history 最新一条的 date。

## 各节写法要点与反例

### 文档控制（引擎生成，不在正文写）
- 被测版本、关联测试计划 / 测试用例、报告日期改为写进 doc.json（related_docs、revision_history），由引擎生成封面文档控制表与修订记录页。要点仍然适用：① 报告日期（revision_history 最新一条的 date）要是实际生成日期，不是计划日期。② 关联测试计划的版本号要与实际执行时使用的版本一致，若测试期间测试计划有过修订，要注明依据哪个版本执行。
- 反例：关联测试计划不写版本号——无法判断本次执行依据的准出标准是哪一版。

### 执行概况
- 要点：① 执行周期给起止日期。② 整体执行率 = 已执行用例数 / 计划用例总数，要给出具体数字，不用"基本执行完毕"这类表述。③ 如果执行率不到 100%，要说明未执行的原因。
- 反例：「本轮测试执行顺利」——没有周期、人员、执行率任何一项具体信息。

### 用例执行统计
- 要点：① 按模块与按优先级两个维度都要给统计，不能只给一个总数。② 通过率要能与测试计划的准出标准直接比对（同一口径：分子分母定义一致）。③ 阻塞与未执行的用例要单独列出并说明原因，不能混入"失败"笼统统计。
- 反例：只给一个"通过率 92%"的总数，不区分模块和优先级——无法判断是否满足"P0 用例通过率 100%"这类分优先级的准出标准。

### 缺陷统计
- 要点：① 级别分布要与测试计划里定义的级别一致，不能报告阶段又出现新级别。② 状态分布（新建 / 处理中 / 已关闭 / 延期）要能反映当前真实状态，不是提交时的快照。③ 发现趋势按时间给出，帮助判断质量是否收敛（后期新增缺陷数下降）还是仍在发散。
- 反例：缺陷统计只给总数，不分级别、不分状态——无法判断是否有未解决的 P0 缺陷，这是准出结论的关键依据。

### 未通过与遗留问题
- 要点：① 每条未通过用例或遗留缺陷都要写清原因（不是"待排查"这种空泛说法）、影响范围、后续计划（修复时间或明确的不修复决定及理由）。② 遗留问题如果决定不修复就上线，必须写清谁批准、依据什么风险评估。
- 反例：「若干用例未通过，正在处理中」——没有具体是哪些用例、什么原因、什么计划，无法支撑准出决策。

### 准出结论与依据
- 要点：① 结论只能是"建议发布""不建议发布""有条件发布（附条件）"三选一，不用模糊措辞。② 依据要逐条比对测试计划的准出标准，标注每一条是否达成。③ 与测试计划口径不一致时（如测试计划要求 P1 通过率 95%，报告却用 90% 作为达标线），属于必改问题。
- 反例：「测试基本完成，建议尽快上线」——"基本完成"不是准出结论，且没有逐条比对依据。

### 风险与建议
- 要点：① 风险要写清"上线后需要关注什么，用什么指标监控，观察多久"，与 PRD 的目标指标或 tech-spec 的可观测性节呼应。② 建议要可执行，不是空泛的"持续关注"。
- 反例：「建议上线后持续观察」——观察什么指标、用什么工具、观察多久，都没写。

### 附录：明细数据引用
- 要点：① 给出完整执行明细（data/execution.csv）与缺陷清单（data/defects.csv）的位置，正文的统计表是汇总视图，不是全部明细。
- 反例：正文声称"完整明细见附件"但没有给出具体路径或链接。
